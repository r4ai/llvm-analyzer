# ADR 006: 短時間性能処理のバッチ計測

## Status

Accepted

## Date

2026-07-27

## Supersedes

なし

## Superseded by

なし

## Context

巨大IRの性能ゲートは、入力を4倍にしたときの処理時間を比較し、正規化増加率が2.0を超えると失敗する。
`file-references`シナリオは一回の処理が数msであり、3回の単発計測では一時停止が中央値へ入り得る。

実際に、同じ実装が正規化増加率0.6で成功した後、別のGitHub Actions実行で3.2となった。
失敗コミットの反復計測では回帰を再現できず、単発計測のばらつきが性能契約の判定を変えていた。

## Decision Drivers

- 単発の一時停止だけでCIを失敗させない。
- 継続する二次時間の増加は従来どおり検出する。
- 閾値と代表入力を変更せず、性能契約を維持する。
- CI時間の増加を、5サンプルの中央値と短時間シナリオのバッチ計測に限定する。

## Considered Options

### 1. 失敗した性能ゲートを再試行する

同じjobまたはベンチマークを、失敗時にもう一度実行する。

得るもの:

- 一時的な失敗が再実行で成功する可能性がある。

失うもの:

- 最初の測定器が不安定なまま残る。
- 実際の回帰も、成功するまでの再試行によって見逃し得る。

### 2. 正規化増加率の閾値を緩める

現在の2.0より大きい値を許容する。

得るもの:

- 一時的な遅延で失敗する回数が減る。

失うもの:

- 入力増加に対する超線形な処理時間を検出しにくくなる。
- 既存の性能契約を弱める。

### 3. 短時間処理をバッチ化して中央値を取る

全シナリオのサンプル数を3から5へ増やす。
短時間処理はウォームアップ後、同じ処理を複数回実行した平均時間を一サンプルとする。
5サンプルの中央値を大小入力の代表値にする。

得るもの:

- 一回の一時停止がバッチ平均で薄まり、単一サンプルの外れ値は中央値から除かれる。
- 継続する遅延は過半数のサンプルへ現れるため、既存閾値で検出できる。

失うもの:

- ベンチマークの実行時間が増える。
- 同じ入力を反復するため、実際の一回実行よりJITが安定した状態を測る。

## Decision

全シナリオのサンプル数を3から5へ増やす。
数msで完了する`file-references`シナリオは、ウォームアップ付きのバッチ計測へ変更する。
バッチ平均の中央値から正規化増加率を計算する。

閾値と入力倍率は変更しない。
数十ms以上かかるシナリオは、追加のバッチ計測を行わない。

## Consequences

良い影響:

- 共有runnerの一時停止による誤検出が減る。
- 継続する超線形な増加は、同じ閾値で検出できる。

悪い影響:

- 全シナリオの計測時間が、追加した2サンプル分だけ増える。
- `file-references`の計測時間がバッチの反復回数に応じて増える。
- 計測回数を変更する場合は、CI時間と外れ値耐性を再評価する必要がある。

中立的な影響:

- 出力する時間は、ウォームアップ後の一回あたり平均時間になる。
- analyzerとparserの外部契約は変わらない。

## Scope

巨大IR性能ゲートの全シナリオへ5サンプルの中央値を適用する。
ウォームアップ付きバッチは、数msの処理時間を比較する`file-references`シナリオだけに適用する。
利用者向けの処理とE2E計測には適用しない。

## Follow-up

- 安定計測helperと単体テストを追加する。
- 巨大IRベンチマーク、現在設計、ロードマップへ反映する。
