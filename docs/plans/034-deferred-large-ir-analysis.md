# 巨大IRの初回解析と要求駆動型推論

## Context

PR #13は、単一トップレベル要素の再パースと解析済みスナップショットの共有を導入した。
一方、約1.58 MiBの代表入力では、初回スナップショット構築に262.9 ms、1文字編集後のインクリメンタル更新に143.0 msかかる。

CPUプロファイルでは、lexerのトークン位置計算と、全SSA値に対する表示用型推論が主要なコストだった。
型推論結果はhover、completion、inlay hintで使うが、診断、定義参照、semantic tokens、outlineの初期構築には不要である。

設計判断は[ADR 004](../adr/004-defer-derived-type-inference.md)に記録する。

## スコープ

今回やること:

- lexerの位置計算を、行開始位置ごとの二分探索からソース順の単調走査へ変更する。
- ASCII識別子の分類と数値パターン列を、トークンごとの一時オブジェクトを作らない形へ変更する。
- SSA値の表示用型を、意味モデル構築時ではなく最初の参照時に一度だけ推定する。
- inlay hintは要求範囲でシンボルを絞ってから型を推定する。
- 初回読み込み、全体更新、インクリメンタル更新、型情報の問い合わせを同じ入力で計測する。

今回やらないこと:

- モジュールスコープの意味モデルを差分更新する可変索引。
- LLVM verifierのインクリメンタル実行。
- 型整合性の完全検証。
- ファイルサイズによるLSP機能の無効化。

## 状態遷移とテスト義務

| 状態     | 操作                                | 次状態           | 検証する契約                   |
| -------- | ----------------------------------- | ---------------- | ------------------------------ |
| 未推定   | 診断、定義参照、outline             | 未推定           | 型推論なしで既存結果を返す     |
| 未推定   | hover、completion、範囲内inlay hint | 推定済み         | 従来と同じ型を返す             |
| 推定済み | 同じ型を再参照                      | 推定済み         | 同じ値を再計算せず返す         |
| 未推定   | 範囲外inlay hint                    | 未推定           | 表示範囲外の型を推定しない     |
| 解析済み | 単一要素内の編集                    | 新しい未推定状態 | 更新後のソースから型を推定する |

テスト義務は、トークン分類の同値性、位置情報の同値性、既存型推論結果の同値性、遅延値の一回評価、inlay hintの範囲先行絞り込み、型を推定できない値の除外、更新後の型再計算の7件とする。

## 検証方法

- lexer、analyzer、language serverの単体テストで外部契約を確認する。
- `pnpm benchmark:large-ir -- --check`で初回読み込みと更新の増加率を確認する。
- 型問い合わせを含むベンチマークで、遅延によって処理が消失したのではなく要求時に完了することを確認する。
- `pnpm test:coverage`、`pnpm typecheck`、`pnpm lint`、`pnpm format`、`pnpm build`を実行する。
- 同じ対象と規則で、本体とテストの認知的複雑度、循環的複雑度、行数、関数数を変更前後で比較する。

## 実装結果

約1.58 MiB、1,600関数、各40命令の代表入力で、初回スナップショット構築は262.9 msから170.4 msへ短縮した。
1文字編集後のインクリメンタル更新は143.0 msから80.9 msへ短縮した。
同じ入力の構文解析は111.4 msから90.8 ms、意味解析は204.1 msから78.3 msへ短縮した。

可視範囲の型問い合わせは11.7 msで完了し、40件以上のInlay Hintsが従来と同じ型を返すことをベンチマーク内で検証した。
入力を4倍にしたときの正規化増加率は、初回読み込み1.1、全体更新1.0、インクリメンタル更新1.0、可視範囲の型問い合わせ1.3だった。

複雑度は、`origin/main`と作業ツリーの`packages/*/src/**/*.ts`および`scripts/*.mjs`をTypeScript ASTで測定した。
循環的複雑度は関数ごとの基礎経路、条件分岐、ループ、case、catch、三項演算子、論理演算子を数えた。
認知的複雑度は構造分岐と論理演算子を数え、構造の入れ子を加算した。
行数はformatter適用後の物理行数であり、公開barrelだけを除外した。

| 対象   | 指標                         |  `origin/main` |         変更後 |
| ------ | ---------------------------- | -------------: | -------------: |
| 本体   | 循環的複雑度の最大値、合計値 |      51、1,276 |      47、1,296 |
| 本体   | 認知的複雑度の最大値、合計値 |      89、1,036 |      85、1,043 |
| 本体   | ファイル数、行数、関数数     | 31、8,846、499 | 32、8,905、511 |
| テスト | 循環的複雑度の最大値、合計値 |        11、572 |        11、582 |
| テスト | 認知的複雑度の最大値、合計値 |        28、104 |        28、104 |
| テスト | ファイル数、行数、関数数     | 18、5,077、490 | 19、5,139、500 |

lexerの正規表現分岐と行位置の二分探索を単純な文字分類と単調走査へ置き換えたため、本体の最大複雑度は下がった。
合計値、コード量、関数数は、遅延値、性能シナリオ、境界テスト、単純な文字分類関数の追加によって増えた。
型推論を問い合わせごとに再実行する案は状態を減らせるが、同じInlay Hintsの再要求で計算を繰り返すため採用しなかった。

未対応のテスト義務`U`は0、義務総数`O`は7、検証済み義務`O_v`は7である。
この変更で追加または分離した論理ケース`T`は5、削除しても検出能力が変わらないケース`T_r`は0である。
独立シナリオの詰め込み`P`、理由のない層間重複`D`、再試行依存`F`は0であり、新しいfixtureとtest doubleは追加していない。

`pnpm test:coverage`は345テストが通過し、statement、branch、function、lineカバレッジはすべて100%だった。
`pnpm format`、`pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm benchmark:large-ir -- --check`も通過した。
VSCode 1.96.0のExtension Host E2Eは9件すべて通過した。
