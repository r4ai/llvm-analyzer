# 巨大IR性能ゲートの安定化

## Context

`file-references`シナリオは、3回の単発計測から求めた中央値を大小入力で割り、正規化増加率を判定している。
GitHub Actionsでは、同じ実装が正規化増加率0.6で成功した後、別の実行で3.2となり失敗した。
失敗時は大入力だけが5.7 msから20.7 msへ増えており、同じコミットのローカル再計測では再現しなかった。

数msの単発計測は、JIT、GC、共有runnerのスケジューリングによる一時停止の影響を受けやすい。
一方、閾値を緩めるだけでは、入力4倍時に処理時間が16倍へ近づく二次増加を見逃す。

計測戦略は[ADR 006](../adr/006-batch-short-performance-measurements.md)に記録する。

## スコープ

今回やること:

- 短時間処理をウォームアップ後に複数回まとめて計測する。
- バッチの平均実行時間を複数回求め、中央値を代表値にする。
- 全シナリオのサンプル数を3から5へ増やし、単発の遅延が中央値にならないようにする。
- `file-references`シナリオへ安定計測を適用する。
- 単発の遅延を除外し、継続する遅延を残す契約を単体テストする。
- CIの正規化増加率閾値`2.0`を維持する。

今回やらないこと:

- 失敗したCIを自動再試行する。
- 性能回帰の閾値を緩める。
- analyzerやparserの処理を変更する。
- 数十ms以上かかる既存シナリオをバッチ計測する。

## 状態遷移とテスト義務

| 状態       | 入力                     | 次状態 | 検証する契約                                 |
| ---------- | ------------------------ | ------ | -------------------------------------------- |
| 未計測     | ウォームアップ回数       | 計測前 | ウォームアップ時間を結果へ含めない           |
| 計測前     | 一定時間の処理           | 計測済 | バッチ時間を実行回数で割った値を返す         |
| 計測前     | 一サンプルだけの遅延     | 計測済 | 中央値が単発の遅延を代表値にしない           |
| 計測前     | 半数を超えて継続する遅延 | 計測済 | 中央値が継続する遅延を代表値にする           |
| 設定受付前 | 0、負数、偶数サンプル数  | 失敗   | 不正な計測設定を補正せず、例外として拒否する |

## 検証方法

- 安定計測helperの単体テストをRed、Greenの順に実行する。
- `pnpm benchmark:large-ir -- --check`を複数回実行し、正規化増加率を確認する。
- `pnpm test:coverage`、`pnpm typecheck`、`pnpm lint`、`pnpm format`、`pnpm build`を実行する。
- 本体とテストの認知的複雑度、循環的複雑度、行数、関数数を同じ規則で変更前後比較する。

## 実装結果

ウォームアップ、バッチ反復、奇数個のサンプル数を受け取る安定計測helperを追加した。
不正な反復設定は`RangeError`として拒否し、既定の単調時計をテスト用の時計へ差し替えられるようにした。

Redではhelperを追加する前に単体テストを実行し、moduleが存在しないため失敗することを確認した。
Greenでは、ウォームアップの除外、バッチ平均、単発遅延の除外、継続遅延の保持、不正設定の拒否を確認した。

巨大IR性能ゲートのサンプル数は3から5へ増やした。
`file-references`は3回のウォームアップ後、25回のバッチを5サンプル測定し、一回あたり平均時間の中央値を返す。
正規化増加率の閾値`2.0`と大小入力は変更していない。

変更後の性能ゲートを5回連続で実行し、すべて成功した。
`file-references`の正規化増加率は0.8、1.1、1.2、1.1、0.9だった。
LSP差分更新を含む他のシナリオも5回すべて閾値内だった。

複雑度は、`packages/*/src/**/*.ts`と`scripts/*.{mjs,mts,ts}`をTypeScript ASTで測定した。
生成物、公開barrel、文書は除外し、同じ測定器で変更前後を比較した。

| 対象   | 指標                         |         変更前 |         変更後 |
| ------ | ---------------------------- | -------------: | -------------: |
| 本体   | 循環的複雑度の最大値、合計値 |      47、1,340 |      47、1,355 |
| 本体   | 認知的複雑度の最大値、合計値 |      85、1,066 |      85、1,074 |
| 本体   | ファイル数、行数、関数数     | 33、9,282、534 | 34、9,345、541 |
| テスト | 循環的複雑度の最大値、合計値 |        11、610 |        11、621 |
| テスト | 認知的複雑度の最大値、合計値 |        28、107 |        28、107 |
| テスト | ファイル数、行数、関数数     | 20、5,464、525 | 21、5,541、536 |

最大複雑度は増えていない。
合計値とコード量は、独立した計測契約、不正設定の検証、計測helperの単体テストによって増えた。
閾値を緩める案とCIを再試行する案は、性能契約または失敗判定を弱めるため採用しなかった。

未対応のテスト義務`U`は0、義務総数`O`は7、検証済み義務`O_v`は7である。
論理ケース`T`は7、削除しても検出能力が変わらないケース`T_r`は0である。
独立シナリオの詰め込み`P`、理由のない層間重複`D`、再試行依存`F`はいずれも0とした。
テストhelperは1個、最大間接深度`I`は1であり、fixture、test double、再試行は追加していない。

`pnpm test:coverage`は368テストが通過し、statement、branch、function、lineカバレッジはすべて100%だった。
`pnpm test`、`pnpm typecheck`、`pnpm lint`、`pnpm format`、`pnpm build`も通過した。
