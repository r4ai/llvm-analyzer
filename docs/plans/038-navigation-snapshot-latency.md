# コードナビゲーションのスナップショット待ち時間

## Context

巨大LLVM IRでは、解析済みスナップショット上のDefinition自体は十分に速い。
一方、ファイルを開いた直後や編集直後のCmd+クリックでは、Language Serverが最新スナップショットを同期生成してからDefinitionを処理する。
約1.58 MB、1,600関数、64,000命令の合成IRでは、この経路が初回約1.18秒、単一関数内の局所編集後でも約0.83秒かかり、Definitionの索引時間よりスナップショット生成待ちがUXを支配している。

スナップショット生成では、意味モデルを公開用へ変換する際にシンボルと参照列を全件複製している。
さらに、Definitionでは使わない置換候補索引も先に構築している。
不変スナップショットの契約を保ったまま重複表現と不要な先行処理を除き、編集直後のコードナビゲーション待ち時間を短縮する。

## スコープ

今回行うことは次のとおり。

- 意味解析中のシンボルを公開時に全件複製せず、解析完了後に読み取り専用として公開する。
- 参照列は必要なシンボルだけをソース順へ整列し、長さ1の参照列を複製しない。
- Definitionで不要なrename／Code Action用置換候補索引を最初の利用時まで遅延する。
- 巨大IRの初回スナップショット、局所編集後スナップショット、編集後Definitionを同じ操作経路で計測する。
- Definition、References、Rename、Hover、診断、Document Symbolsなどの既存結果契約を維持する。

今回行わないことは次のとおり。

- LSPの返却件数や検索範囲を狭めない。
- 古いスナップショットから結果を返さない。
- parser、名前解決、診断の規則を変更しない。
- worker threadや部分的な意味解析を追加しない。単純な表現削減で目標に届かない場合は別の設計判断として扱う。

## 検証方法

探索から得た状態と操作の組合せを次のように検証する。

| 状態                             | 操作                               | 結果契約                     | 性能契約                                         |
| -------------------------------- | ---------------------------------- | ---------------------------- | ------------------------------------------------ |
| 解析済み巨大IR                   | Definition、References             | 従来と同じ定義と参照列を返す | 問い合わせ時間は既存上限を維持する               |
| 未解析の巨大IR                   | 初回スナップショット後のDefinition | 最新テキストの定義へ移動する | 初回生成時間を短縮する                           |
| 単一関数内を編集                 | インクリメンタル更新後のDefinition | 編集後の位置と定義を返す     | 全体再構築より速く、変更前より待ち時間を短縮する |
| 前方参照、ラベル、モジュール参照 | References、Rename                 | 全出現をソース順で返す       | 問い合わせごとに再整列しない                     |
| 同一スナップショット             | Code Action、Rename候補            | 従来と同じ候補を返す         | 置換候補索引は一度だけ構築する                   |

次のコマンドを実行する。

```sh
pnpm benchmark:large-ir -- --check
pnpm test:coverage
pnpm typecheck
pnpm lint
pnpm format
pnpm build
pnpm --filter llvm-analyzer-vscode test:e2e
pnpm changeset status --since=origin/main
```

変更前後は同じNode.js、同じ合成IR、同じサンプル数で測定する。
性能値に加え、本体とテストの認知的複雑度・循環的複雑度の最大値と合計値、行数、関数数、テスト義務を記録する。

## 実装結果

意味シンボルは、解析中の可変な参照追加と解析後の読み取り専用公開を一つのクラスで扱うようにした。
公開用オブジェクトへの全件変換と、全シンボルに対する参照配列の複製を除いた。

未参照シンボルはDefinitionだけで使われる限り参照配列を作らない。
ReferencesまたはRenameが参照列を要求した時点で、定義と追加参照から読み取り専用配列を一度だけ作る。
前方参照によってソース順でない場合だけ整列し、通常のSSA定義と後続参照では追加順をそのまま使う。

型推論は要求駆動のまま維持した。
シンボルごとのクロージャと`Object.defineProperty`を廃止し、共有getterが保持したASTノードから最初の要求時に型を推定する。

性能ゲートは、初回snapshotとDefinitionを500 ms以下、単一関数内の局所編集後snapshotとDefinitionを150 ms以下とした。
macOSのローカル実測は125.3 msと33.8 msだったが、GitHub Ubuntu runnerではparserとanalyzerが約3倍遅く、375.8 msと98.0 msだった。
CIの絶対上限は後者を基準にし、入力4倍時の正規化増加率と全体再構築に対する高速化率を独立して検査する。
5 ms未満の短時間操作は倍率に対するノイズ床を使い、20 msの対話操作上限も独立して検査する。
snapshot共有は相対値だけに依存せず、1.2倍以上の高速化と50 ms以上の重複解析削減を検査する。

### 性能

Node.js 26.1.0で、約1.58 MB、1,600関数、64,000命令の合成IRを5回測定した中央値を使った。

| 操作                           |     変更前 |   変更後 | 短縮率 |
| ------------------------------ | ---------: | -------: | -----: |
| 初回snapshotとDefinition       | 1,179.7 ms | 125.3 ms |  9.4倍 |
| 全体再構築後のDefinition       | 1,185.4 ms | 139.4 ms |  8.5倍 |
| 局所編集後snapshotとDefinition |   834.2 ms |  33.8 ms | 24.7倍 |
| 表示範囲の型問い合わせ         |     1.0 ms |   0.1 ms | 10.0倍 |
| 共有snapshotと全索引登録       | 1,271.9 ms | 122.9 ms | 10.3倍 |

解析済みsnapshot上のDefinitionは初回0.012 ms、再要求0.001 ms未満だった。
16,001件を返すReferencesは初回1.113 ms、再要求0.320 msだった。
すべての性能ゲートで結果件数を検査し、返却件数や検索範囲は変更していない。

### 複雑度

`origin/main`と変更後の`packages/*/src/**/*.ts`および`scripts/*.mjs`を、同じTypeScript AST規則で測定した。
循環的複雑度は基礎経路、条件分岐、ループ、case、catch、三項演算子、論理演算子を数えた。
認知的複雑度は構造分岐と論理演算子を数え、構造の入れ子を加算した。
行数はformatter適用後の物理行数である。

| 対象   | 指標                         |   `origin/main` |          変更後 |
| ------ | ---------------------------- | --------------: | --------------: |
| 本体   | 循環的複雑度の最大値、合計値 |       47、1,472 |       47、1,481 |
| 本体   | 認知的複雑度の最大値、合計値 |       85、1,173 |       85、1,183 |
| 本体   | ファイル数、行数、関数数     | 42、10,060、582 | 42、10,157、583 |
| テスト | 循環的複雑度の最大値、合計値 |         11、626 |         11、626 |
| テスト | 認知的複雑度の最大値、合計値 |         28、107 |         28、107 |
| テスト | ファイル数、行数、関数数     |  21、5,630、541 |  21、5,630、541 |

本体の最大複雑度は増えていない。
合計値、行数、関数数の増加は、意味シンボルの要求駆動表現と性能上限、ノイズ床、snapshot共有の絶対削減ゲートによる。
シンボルごとのクロージャ、公開用シンボル複製、未参照レジスタの参照配列という重複表現を除いたため、状態と割り当て総数は減っている。

未対応のテスト義務`U`は0、対象義務`O`は8、検証済み義務`O_v`は8である。
追加した性能論理ケース`T`は3、削除しても検出能力が変わらないケース`T_r`は0である。
独立シナリオの詰め込み`P`、理由のない層間重複`D`、再試行依存`F`は0であり、fixtureとtest doubleは追加していない。
ミューテーションテスト`M`は実行器がないため未測定とした。
