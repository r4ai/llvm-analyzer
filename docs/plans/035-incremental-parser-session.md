# 計算量契約を持つインクリメンタルparser session

## Context

現在の`updateParseResult`は、更新前後のソースを先頭と末尾から比較して変更範囲を推定する。
その後、トップレベル要素を線形探索し、単一要素に収まる場合だけ局所再パースする。

この方式では、LSPが差分変更を通知しているにもかかわらず、変更範囲の発見にソース全体の`O(n)`時間がかかる。
対象要素の探索も要素数`m`に対して`O(m)`であり、局所更新の計算量契約がAPIに現れない。

`n`をソース長、`m`をトップレベル要素数、`k`を再パースする要素長、`a_s`を位置が移動する後続ASTノード数とする。
設計判断は[ADR 005](../adr/005-explicit-edit-incremental-parser-session.md)に記録する。

## スコープ

今回やること:

- 更新前の範囲と挿入後の終端位置を持つ明示的な編集型をparserへ追加する。
- ソース、構文解析結果、直前の更新戦略を所有する不変なparser sessionを追加する。
- トップレベル要素を二分探索し、単一要素内の編集だけを局所再パースする。
- LSPの`contentChanges`を保持し、debounce中の複数変更を順番どおりparser sessionへ渡す。
- 全文変更、変更列の不整合、要素境界の破壊では全文解析へ戻す。
- 既存の`parseModule`と`updateParseResult`の結果契約を維持する。

今回やらないこと:

- 公開ASTを相対位置またはgreen treeへ変更する。
- モジュール全体の意味モデルを差分更新する。
- 位置が動く後続ASTを永続木で遅延移動する。
- 複数の独立したトップレベル要素を一回の編集で局所再パースする。

## 計算量契約

| 操作                                 |                     時間 |         追加空間 | 条件                                    |
| ------------------------------------ | -----------------------: | ---------------: | --------------------------------------- |
| 初回解析                             |                   `O(n)` |           `O(n)` | lexer、parserとも前方向へ走査する       |
| 同じ長さの単一要素内編集             |       `O(log m + k + m)` |       `O(k + m)` | 対象探索、要素再解析、公開AST配列再構成 |
| 長さまたは行数が変わる単一要素内編集 | `O(log m + k + m + a_s)` | `O(k + m + a_s)` | 後続ASTの絶対位置を移動する             |
| 境界を確定できない編集               |                   `O(n)` |           `O(n)` | 全文解析へ戻す                          |

公開ASTが絶対位置を持つ配列であるため、局所編集でも新しいModuleを返すには`O(m)`の配列再構成が残る。
この制約を隠して`O(k)`とは記載しない。

## 状態遷移とテスト義務

| 現状態   | 入力                 | 次状態      | 更新戦略      | 検証する契約                       |
| -------- | -------------------- | ----------- | ------------- | ---------------------------------- |
| 初期化前 | 全文                 | 解析済み    | `initial`     | 全文解析と同じ結果                 |
| 解析済み | 同一ソース           | 同じsession | 変更なし      | オブジェクトを再生成しない         |
| 解析済み | 単一要素内の同長編集 | 解析済み    | `incremental` | 前後要素を再パースしない           |
| 解析済み | 単一要素内の伸縮編集 | 解析済み    | `incremental` | 後続範囲を正しく移す               |
| 解析済み | 要素間または境界破壊 | 解析済み    | `full`        | 全文解析と同じ結果                 |
| 解析済み | 全文LSP変更          | 解析済み    | `full`        | 通知本文を正準ソースにする         |
| 解析済み | 連続する複数LSP変更  | 解析済み    | 各変更に従う  | 通知順に適用した全文解析と同じ結果 |
| 解析済み | 不正な範囲           | 失敗        | 例外          | 不正入力を補正しない               |

## 検証方法

- parser sessionの状態遷移を単体テストで検証する。
- 局所更新、伸縮、境界破壊、複数変更について、結果を`parseModule`と比較する。
- language serverのスナップショットで、明示的編集を使った結果と全文再構築の全契約を比較する。
- 巨大IRベンチマークでparser strategy、再パースbyte数、初回読み込み、編集後の時間を記録する。
- `pnpm test:coverage`、`pnpm typecheck`、`pnpm lint`、`pnpm format`、`pnpm build`、Extension Host E2Eを実行する。
- 本体とテストの認知的複雑度、循環的複雑度、行数、関数数を同じ規則で比較する。

## Results

`IncrementalParserSession`を追加し、ソース、`ParseResult`、更新戦略、再パースbyte数を一つの不変オブジェクトへまとめた。
明示的な編集ではトップレベル要素を二分探索し、互換入口だけが更新前後の全文から差分を推定する。

language serverはLSPの`contentChanges`をバージョン付きジャーナルへ記録する。
150msのdebounce中に複数通知が届いても、連続する変更列を通知順にsessionへ適用する。
バージョンまたは最終テキストが一致しない場合は全文解析へ戻る。

初回`O(n)`の監査では、横に広い不正命令に含まれる参照ごとにopcodeを再走査する二次時間経路を発見した。
opcodeを要素ごとに一度だけ求め、`blockaddress`の局所構文を固定位置で判定するように変更した。
7,577 bytesから120,077 bytesへ16倍にした回復シナリオの正規化増加率は、Redの4.6から0.8へ下がった。
大きい入力の構文解析時間は444.6 msから6.5 msへ短縮した。

約1.58 MiB、1,600関数、各40命令の代表入力では、初回スナップショット構築は156.4 ms、局所編集は83.5 ms、全文再構築は164.8 msだった。
局所編集は全文再構築より2.0倍速く、各編集で再パースした量は985 bytesだった。
入力を4倍にしたときの正規化増加率は、初回読み込み1.1、全文再構築1.1、局所編集1.4、可視範囲の型問い合わせ1.1だった。

同じ測定器で、直前コミットと変更後の複雑度を比較した。

| 対象   | 指標                         |   直前コミット |         変更後 |
| ------ | ---------------------------- | -------------: | -------------: |
| 本体   | 循環的複雑度の最大値、合計値 |      47、1,296 |      47、1,340 |
| 本体   | 認知的複雑度の最大値、合計値 |      85、1,043 |      85、1,069 |
| 本体   | ファイル数、行数、関数数     | 32、8,873、511 | 33、9,245、534 |
| テスト | 循環的複雑度の最大値、合計値 |        11、582 |        11、610 |
| テスト | 認知的複雑度の最大値、合計値 |        28、104 |        28、107 |
| テスト | ファイル数、行数、関数数     | 19、5,120、500 | 20、5,444、525 |

最大複雑度は増えていない。
合計値とコード量は、session、変更ジャーナル、計算量ベンチマーク、状態遷移テストの追加分だけ増えた。

未対応のテスト義務`U`は0、義務総数`O`は16、検証済み義務`O_v`は16である。
この変更で追加または分離した論理ケース`T`は16、削除しても検出能力が変わらないケース`T_r`は0である。
独立シナリオの詰め込み`P`、理由のない層間重複`D`、再試行依存`F`は0であり、新しいfixtureとtest doubleは追加していない。

`pnpm test:coverage`は361テストが通過し、statement、branch、function、lineカバレッジはすべて100%だった。
`pnpm format`、`pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm benchmark:large-ir -- --check`も通過した。
VSCode 1.96.0のExtension Host E2Eは9件すべて通過した。
