# プラン: 差分編集後のLSP性能計測

## Context

巨大LLVM IRの初回解析に加えて、LSPが差分変更を受け取った後の再解析時間も継続して確認する必要がある。
現在のlanguage serverは差分同期を受け取るが、変更後のparserとanalyzerはドキュメント全体から不変スナップショットを再構築する。

## スコープ

- 巨大IRの初回スナップショット作成時間を計測する。
- 一文字の差分編集を複数位置へ適用し、変更後のスナップショット再構築時間を計測する。
- 再構築後にDefinition問い合わせが成立することを検証する。
- 既存の巨大IRベンチマークをCIで実行する。
- parserとanalyzerを差分解析方式へ変更しない。
- 時間に依存する単一の絶対値を性能契約にしない。

## 検証方法

- `pnpm benchmark:large-ir -- --check` で初回読み込みと差分編集後の正規化増加率を確認する。
- `pnpm test:coverage`、`pnpm typecheck`、`pnpm lint`、`pnpm format`、`pnpm build` を実行する。
- GitHub Actions上で巨大IRベンチマークが成功することを確認する。

## 実装結果

LSPライフサイクルのシナリオでは、約394 KBと約1.58 MBのIRを使い、初回スナップショット作成と三回の一文字編集後の再構築を分けて計測した。
各再構築後にはDefinition問い合わせを実行し、編集後の意味モデルが利用できることも確認した。

入力を4倍にしたときの正規化増加率は、初回読み込み1.1、差分編集後1.1だった。
既存の多数関数、同一グローバル大量参照、ファイル参照抽出も、正規化増加率0.7、0.7、1.0で検査を通過した。

同じTypeScript AST計測では、本体の循環的複雑度は最大52のまま、合計1,370から1,384になった。
本体の認知的複雑度は最大84のまま、合計986から993になった。
本体は8,592行、458関数から8,674行、465関数になった。
テストは循環的複雑度が最大11、合計605、認知的複雑度が最大28、合計118、4,725行、488関数のまま変わらなかった。

テスト義務は、初回スナップショット作成、差分編集後の再構築、編集後のDefinition解決の三件とした。
未対応の契約項目は0件で、三件すべてをベンチマークで検証し、冗長な論理ケースは0件だった。

`pnpm test:coverage` は281テストが通過し、statement 95.92%、branch 88.19%、function 99.2%、line 98.26%だった。
`pnpm typecheck`、`pnpm lint`、`pnpm format`、`pnpm build`、`pnpm benchmark:large-ir -- --check` も通過した。
