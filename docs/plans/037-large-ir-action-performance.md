# 巨大LLVM IRの操作性能

## Context

初回解析と差分解析は入力サイズに対して線形化されているが、解析後のLSP操作には全シンボル走査、参照列の再整列、関数列の線形探索が残っている。
このため、巨大IRではコードジャンプ、Hover、補完、Inlay Hintsなどの操作が解析済みスナップショットを使っていても入力全体の大きさに影響される。

操作結果の大きさに依存しない位置問い合わせは対数時間、範囲問い合わせは範囲内の結果数に比例する時間、全件を返す問い合わせは入力と出力に対する線形時間を性能契約とする。
合成した巨大IRで各操作の待ち時間と入力4倍時の増加率を計測し、エディタ操作として知覚しにくい待ち時間へ抑える。

## スコープ

今回行うことは次のとおり。

- Definition、References、Hover、Renameで参照列を再整列または線形探索する処理を除く。
- Completion、Inlay Hints、Code Action、CFG位置検索を位置または範囲索引へ接続する。
- Document Symbols、Semantic Tokens、Folding Rangesの不変スナップショット由来の結果を再利用する。
- Workspace SymbolsとCall Hierarchyに問い合わせ用索引を持たせ、問い合わせごとの全再走査を除く。
- Document Linkの候補抽出結果を解析済みスナップショットで再利用する。
- FormattingとRange Formattingを含む主要アクションを巨大IRベンチマークへ追加する。

次の変更は行わない。

- LSPの返却件数や既存の検索範囲を狭めない。
- IRの解析規則、名前解決規則、診断規則を変更しない。
- Workspace SymbolsやCall Hierarchyの曖昧な同名シンボル解決規則を変更しない。
- 全文を返す操作を部分結果や独自プロトコルへ変更しない。

## 検証方法

状態と操作の組合せを次のように検証する。

| 状態                     | 操作                                                     | 性能契約                                                             | 結果契約                                     |
| ------------------------ | -------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------- |
| 多数関数                 | Definition、Hover、Completion、Inlay Hints、CFG位置検索  | 位置問い合わせは対数時間、範囲問い合わせは範囲内結果数に比例         | 小規模IRと同じ位置、内容、候補を返す         |
| 単一シンボルへの大量参照 | References、Rename                                       | 参照数に対する線形時間                                               | 宣言指定と全編集範囲を保持する               |
| 多数シンボル             | Document Symbols、Semantic Tokens、Folding Ranges        | 入力と返却件数に対する線形時間、同一スナップショットでは再構築しない | 順序と分類を保持する                         |
| 複数ファイル索引         | Workspace Symbols、Call Hierarchy                        | 登録時に索引化し、問い合わせ時の無関係な全件走査を除く               | 既存の検索、incoming、outgoing結果を保持する |
| 多数トップレベル要素     | Document Link、Formatting、Range Formatting、Code Action | 全文操作は線形時間、範囲操作は対象範囲中心                           | 安全境界と編集内容を保持する                 |

次のコマンドを実行する。

```sh
pnpm benchmark:large-ir -- --check
pnpm test
pnpm test:coverage
pnpm typecheck
pnpm lint
pnpm format
```

性能ベンチマークでは、操作結果の件数を検査した上で、代表的な巨大IRに対する操作時間の上限と入力4倍時の増加率を確認する。
全件操作の増加率は、JITとGCによる数ms単位の揺らぎを倍率へ増幅しないよう、小さい入力の測定値に10 msのノイズ床を設ける。
このノイズ床とは独立して、巨大IRに対する初回生成時間を100 ms以下に制限する。
変更前後の認知的複雑度、循環的複雑度、コード量、テスト義務も同じ範囲と設定で記録する。

## 実装結果

analyzerの意味モデルへ、解決済み出現、定義終端、可視スコープ、関数範囲の索引を追加した。
DefinitionとHoverは出現索引、Inlay Hintsは定義範囲索引、CompletionとCode Actionはスコープと名前索引、CFGは関数範囲索引を使う。
References、Rename、Semantic Tokensは意味解析時に整列した参照列を再利用し、問い合わせ時の再整列を除いた。

Language ServerはWorkspace Symbolの三文字索引とCall Hierarchyのcaller別、callee別索引を登録時に作る。
Document Symbols、Semantic Tokens、Folding Ranges、Document Link候補は不変snapshotをキーに再利用する。
Range Formattingは選択行の断片だけを整形する。
VSCode拡張のCFG commandは独自LSP requestへ移し、拡張ホストでの全文再解析を除いた。

### 性能

Node.js 26.1.0で、約1.58 MB、1,600関数、各40命令の合成IRを3回測定した中央値を使った。
初回時間は同じsnapshotで最初に操作した時間、再要求時間は初回後の中央値である。

| 操作                     | Redの操作時間 | 変更後の初回時間 | 変更後の再要求時間 |
| ------------------------ | ------------: | ---------------: | -----------------: |
| Definition               |    0.0 ms未満 |         0.012 ms |           0.001 ms |
| Hover                    |    0.0 ms未満 |         0.037 ms |           0.003 ms |
| 表示範囲Inlay Hints      |        9.2 ms |         0.153 ms |           0.007 ms |
| Range Formatting         |        7.4 ms |         0.024 ms |           0.009 ms |
| CFG                      |        未測定 |         0.015 ms |           0.001 ms |
| 完全一致Workspace Symbol |        3.0 ms |         0.014 ms |           0.002 ms |
| Code Action              |        4.6 ms |         0.035 ms |           0.016 ms |
| Document Links           |        未測定 |         0.157 ms |           0.009 ms |
| References、16,001件     |        1.0 ms |         1.106 ms |           0.419 ms |
| Rename、16,001件         |        1.3 ms |         1.196 ms |           1.065 ms |
| Completion               |        3.1 ms |         0.075 ms |           0.052 ms |
| Document Symbols         |       16.4 ms |        16.453 ms |       0.001 ms未満 |
| Semantic Tokens          |       27.9 ms |        11.767 ms |       0.001 ms未満 |
| Folding Ranges           |        0.1 ms |         0.193 ms |       0.001 ms未満 |
| 全文Formatting           |        3.3 ms |         4.305 ms |           5.102 ms |

結果件数が一定の対話操作は、1.58 MB入力ですべて20 ms未満だった。
全件操作の初回生成も100 ms未満だった。
入力4倍時の増加率は、結果件数が一定の操作で最大1.1、10 msのノイズ床を適用して出力件数を正規化した操作で最大0.4だった。

Referencesと全文Formattingの初回時間は短縮していない。
これらは返却する16,001件のLocation生成と全文走査が必要であり、計算量は線形のまま維持した。
Referencesは再整列を除き、同じ参照列を使うRenameとともに出力件数を正規化した増加率を検査する。

### 複雑度

直前コミットと変更後の`packages/*/src/**/*.ts`および`scripts/*.mjs`を同じTypeScript AST規則で測定した。
循環的複雑度は基礎経路、条件分岐、ループ、case、catch、三項演算子、論理演算子を数えた。
認知的複雑度は構造分岐と論理演算子を数え、構造の入れ子を加算した。
行数はformatter適用後の物理行数である。

| 対象   | 指標                         |   直前コミット |          変更後 |
| ------ | ---------------------------- | -------------: | --------------: |
| 本体   | 循環的複雑度の最大値、合計値 |      47、1,340 |       47、1,451 |
| 本体   | 認知的複雑度の最大値、合計値 |      87、1,012 |       87、1,097 |
| 本体   | ファイル数、行数、関数数     | 41、9,437、534 | 42、10,060、582 |
| テスト | 循環的複雑度の最大値、合計値 |        11、684 |         11、700 |
| テスト | 認知的複雑度の最大値、合計値 |        28、123 |         28、123 |
| テスト | ファイル数、行数、関数数     | 21、5,763、583 |  22、5,929、599 |

最大複雑度は増えていない。
合計値、行数、関数数は、操作索引、独自LSP request、全操作を検査する性能シナリオ、契約テストの追加によって増えた。
操作ごとに全文走査する短い案は状態を減らせるが、結果件数が一定の問い合わせを巨大IRの大きさから切り離せないため採用しなかった。

未対応のテスト義務`U`は0、義務総数`O`は18、検証済み義務`O_v`は18である。
この変更で追加または分離した論理ケース`T`は13、削除しても検出能力が変わらないケース`T_r`は0である。
独立シナリオの詰め込み`P`、理由のない層間重複`D`、再試行依存`F`は0であり、新しいfixtureとtest doubleは追加していない。
ミューテーションテスト`M`はリポジトリに実行器がないため未測定とした。

`pnpm test:coverage`では381件が通過し、statement、branch、function、lineカバレッジはすべて100%だった。
